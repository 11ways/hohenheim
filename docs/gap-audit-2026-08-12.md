# Hohenheim design corpus vs implementation — final synthesis

**Scope:** 688 design clauses across `docs/instance-tier-plan.md`, three use-inventories (Pterodactyl, Proxmox, Coolify), the red-team manifest, the recoverable-secret inventory, the roadmap, and the architecture/API docs, verdicted against source in `hohenheim` and the `javaweb` framework chain.

**Result:** 562 clauses confirmed satisfied outright; 24 of the 124 raised findings were refuted on verification (those clauses are satisfied too), leaving **≈586 of 688 satisfied — about 85%**. 100 findings survived adversarial verification.

**The honest headline:** this corpus is substantially implemented. Of the 100 surviving findings, roughly **45 are documentation accuracy** (a document is stale, overclaims, or *understates* what shipped), **~30 are missing mechanism or operability gaps**, **~15 are test-evidence gaps** where the behaviour is correct but the named proof does not prove it, **~8 are security-flavoured** of which **3 are reachable in production today**, and **exactly one is a confirmed silent-behaviour defect** (backup/restore). There is no unauthenticated hole, no privilege-escalation primitive, and no cross-tenant boundary breach anywhere in the 100.

I re-verified the load-bearing claims at file:line myself before writing this. Corrections to the brief and to individual auditors are noted inline.

## Section 1 — Clauses the DOCUMENT was edited to drop rather than the CODE built to satisfy them

This is the specific question asked. Nine cases, ranked by how much scope left the plan.

### 1.1 The at-rest-encryption narrowing was REVERSED, not applied (highest value)

- **Promised:** `instance-tier-plan.md:802-805` instructed, as a Phase 0 action item, that `architecture-stacks.md`'s "secrets are encrypted at rest" be **narrowed** to a stacks-only claim, because it was misleading as a platform claim.
- **What happened:** commit `6b6b2fa0` (2026-08-11) deleted the narrowing. `git show acfff9af:docs/architecture-stacks.md` line 24 previously read *"STACK secrets are encrypted at rest — this is a stacks-only claim, not a platform one"* with lines 31-32 listing site settings and environment variables as explicitly **not** encrypted. The replacement I read at `docs/architecture-stacks.md:65-66` now says: **"Secrets are encrypted at rest, platform-wide — this is NOT a stacks-only claim."** The plan was then amended at `:806-811` to say "DONE 2026-08-11, but the OTHER way round … **Do not re-narrow that document**."
- **The code contradicts the new claim.** I verified: `SiteModel.SETTINGS` is a plain JSON `SchemaField` (`SiteModel.java:57-62`); zenit structurally refuses encryption inside a JSON sub-schema (`zenit/.../orm/model/Schema.java:196-207`). The largest secret surface in the product therefore stores **cleartext at rest** with `.secret()` redaction only. `NodeSiteType.java:67-83` says so in the product's own words: *"the map is the largest plaintext-secret surface in hohenheim (operators put DATABASE_PASSWORD-grade values in it) and it lives in a JSON SchemaField, so **encryption is impossible** and derived-surface redaction is its ONLY control."* Same for `api_keys` (`NodeSiteType.java:87-90`), Java/Command/Docker site types, and `GitSourceSchema` build/preview env maps.
- **Three other documents forbid the claim**, one of them written *the next day*: `phase0-red-team-manifest.md:887` ("The prohibition stands unchanged: no text may claim platform-wide encryption. Item 5 remains OPEN"), `recoverable-secret-inventory.md:146` ("Any claim of 'platform-wide encryption at rest' that does not say this out loud is theater") and `:327`.
- **To close:** restore one sentence to `architecture-stacks.md:65-79` naming what is *not* covered (every JSON-nested secret: site `environment_variables`, `api_keys`, git webhook secret, dev registration token; plus the keyring co-located with the plaintext settings directory), **and delete the "Do not re-narrow that document" instruction at `instance-tier-plan.md:810-811`, which currently forbids the correction.** Alternatively migrate site env vars onto typed rows the way `InstanceVariableModel` already did, and the claim becomes true.
- *Severity: documentation-only — no code path is defective. But an operator who reads it and skips DB-file protection is the harm.*

### 1.5 "Sandboxed builders outside the control-plane trust domain" reinterpreted 36 minutes after the confinement landed

Confinement code `5d3a0ed5` 14:15; the doc block that redefines the gate `f357bbf4` 14:51, conceding "The gate clause reads true now for … NOT as 'the build runs in a sandbox'" (`:4510-4513`). ## Section 2 — Ranked findings

### TIER A — falsifies a stated claim a reader would act on

**A1. Backup manifest omits template binding, variables, config files and crash policy — restore-to-new silently produces a degraded instance, and both gate tests are structurally unable to notice.**
*The single most serious behavioural defect in the audit.*
- Promised (`:3182-3187`, gate at `:3188-3198`): "Every backup carries a versioned manifest: runtime/template version, image digest, instance config, **variables** and secret references, volume inventory, ownership, resource limits" and restore-to-NEW arrives "with its manifest/config/data intact".
- Exists: I verified `BackupManifest.java:34-46` is a 13-component record — **no template id, no template version, no variable inventory**. `buildManifest` (`InstanceBackups.java:550-573`) reads the **raw** stored settings map, even though the `Resolved` it is handed already carries the merged variables. `restoreToNew` writes exactly four columns — NAME, KIND, SETTINGS, SERVER_ID (`:342-347`). So `TEMPLATE_ID`, `CRASH_POLICY` (defaults back to `crash_none`), `ENVIRONMENT_ID`, `BACKUP_TARGET_ID`, every `instance_variables` row and every `instance_files` row are gone. `InstanceService.stageConfigFiles` returns early on an empty file list, so the restored instance deploys with zero config files **and no refusal**.
- The manifest class's own docblock is false: `BackupManifest.java:13-16` claims "full settings (variables and secret values included)".
- **The gate tests cannot fail on this.** Both create a *bare* instance row (`InstanceSnapshotBackupLiveTest.java:132-138`), put a plain `environment_variables` entry in SETTINGS, then assert "secret variables intact" against that same settings entry (`:326-334`). The assertion passes identically against the defect.
- Real product path: `InstanceBackupResource.java:83-106`, a confirmed admin row action. On the plan's own default shape ("Templates are the DEFAULT source of instance images", `:3350`), a restored Velocity proxy comes back with no forwarding-secret row, no `velocity.toml`, no readiness line, no console stop command, and crash-restart silently downgraded to none.
- **Close:** add template id+version, the `instance_variables` inventory (secrets ride inside the already-encrypted `.hib`) and `instance_files` rows to the manifest; have `restoreToNew` re-materialize them and re-stamp crash policy; rewrite one gate journey to back up an instance **created from a template** with a declared secret variable and assert the variable row and config file exist on the restored record.

**A2. Platform-wide encryption claim.** See §1.1. Documentation-only, but it is a security posture claim three other documents forbid.

**A3. An admin-scoped API key can download the TLS PRIVATE KEY.**
- Promised: `:534-536` records as an accepted residual only that "an admin-scoped API key can read admin HTML today", with open decision (3) scoped to `/admin/**` GETs.
- Exists: I verified `HohenheimEndpoints.java:272-280` declares `GET certificates/{id}/download` with `.requiresPermission("hohenheim.admin.access")` and **no** `requiresInteractiveLogin()`; the handler at `HohenheimHandlers.java:332-346` concatenates `CERTIFICATE_PEM` **and** `PRIVATE_KEY_PEM` into the download. Being a GET, no CSRF layer intervenes. `grep requiresInteractiveLogin src/` returns **zero production declarations** (one test comment). The zenit-cms half of decision (3) *is* closed — every generated panel GET carries it (`CmsEndpoints.java:100, :114, :130, :164`).
- Precondition: the key's owner already holds `hohenheim.admin.access` and the key's scope covers it. This is a credential-mode / blast-radius widening (a long-lived non-interactive token reaches a private key), not cross-privilege escalation. Same shape at `:193-199` (instance-template export) and the git-provider browse GETs.
- **Close:** mark the secret-bearing hohenheim GETs `requiresInteractiveLogin()`, or restate decision (3) at `:1130` in terms of what is actually reachable: TLS private keys, template exports, git browsing.

**A4. Phase 0.A cannot be declared complete on its own terms — one gate row has no counterfactual at all.**
- The gate (`:1151-1156`) requires, for every row, a named automated test **plus** a demonstrated counterfactual **plus** a recorded command and tested commit. Every row has a real, non-vacuous test (I confirmed the auditors read the bodies).
- The genuine violation is narrower and worse than "not re-observed": the **Published shell** row (`phase0-red-team-manifest.md:191-202`) has *no counterfactual at all* — it says only "this gate PASSED the fourth audit unchanged and was not reworked" — contradicting the manifest's own header at `:8-9`. `instance-tier-plan.md:1014-1016` states it plainly: "0.5 published shell: NOT EVIDENCE. The only manifest row with no observed counterfactual."
- Additional defect: that row's recorded command is `zenit-dev test --browser --class PublishedEndpointSafetyTest`, but the class lives in `plumage/src/test/` — the **unit** lane. The recorded command names the wrong lane.
- **Refuted sub-claims:** "three counterfactuals not re-observed at HEAD" is a weakening of evidence, not a clause violation (the clause says *demonstrated*, not *re-demonstrated*); and retiring the manifest's drift index violates nothing, since the clause asks for command + commit, both of which are supplied.
- Drift is worse than recorded: `git rev-list --count f38c8d9..HEAD` in hohenheim is **293** today, not the 281 the manifest states.

**A5. The shared_container operator acknowledgement — a declared Phase 3 ENTRY blocker — was never built, and neither was the workload-trust half of the same clause.**
- Promised (`:2521-2529`, and open decision 8 at `:5947-5950`): "Every workload declares trusted/operator-owned vs hostile-tenant. Placement refuses a hostile workload when the host posture cannot satisfy it… The acknowledgement records actor, timestamp and warning version; a boolean hidden in settings is not sufficient."
- Exists: I read `ServerModel.java:99-118` — the AIDEV-NOTE says "the shared_container acknowledgement record (actor, timestamp, warning version — the plan's requirement) is **NOT built yet**; until it is, setting shared_container is a bare admin edit". POSTURE is a plain `EnumField` written by an ordinary CMS form submit (`ServerResource.java:193`). No acknowledgement table, column, action or migration exists. **`ServerModel` registers no behaviours at all**, so not even a revision trail.
- The **workload-trust dimension is also absent**: `grep -rni 'hostile|workload_trust|trust_level' src/` returns only comments. Placement reads POSTURE in exactly one place (`InstancePlacement.java:246`) and only for DEDICATED exclusivity.
- What *is* built: the REFUSE half (`ServerModel.acceptsTenantWorkloads` + `HostAdmission.java:44-49` `host_posture_refuses`), the preflight battery, and on Incus an additional kernel-lane gate. Mitigations: the enum label reads "Shared containers (operator risk)"; the framework activity log captures actor+timestamp on the row (but policy `ACTIVITY`, so no field delta, no warning version).
- Consequence: the phase gate step "two hostile tenant fixtures are refused co-location on an unacknowledged container host" (`:2600-2601`) **has no mechanism to test** — there is no acknowledged/unacknowledged distinction.
- Phases 3–8 all shipped without decision 8 being answered.

### TIER B — security

**B1. Post-start Incus isolation window (EXPLOITABLE, bounded to ≤5 min).** `:4856-4863` names the closure — a listener on the daemon's `/1.0/events` re-verifying within a second — and says "NOT built here". Confirmed absent: the only `openWebSocket` consumers are the operation/console socket. The only bound is `VerifyIncusIsolation`'s `*/5 * * * *` cron. Measured base rate 2 of 34 VM instances; guest-initiated resets only — every product-initiated start re-runs `requireKernelIsolation`. *One auditor claim struck: `HostAdmission.requireKernelTruth` refuses tenant placement on any lane-less Incus host, so the "silent return on a lane-less host" is not a second hole.*

**B2. A RUNNING workload the daemon can address but names no live interface for is recorded as an error and left running.** `IncusKernelIsolation.java:201-207` throws when `liveTaps` is empty; `VerifyIncusIsolation.java:158-163` does `errors.add(...); continue;` — no stop, no repair, no distinction from an unreadable host. The daemon evidence the plan cites (`:4805-4812`, "device name is empty") is the daemon losing the *name* while a tap can still exist in the kernel: a running guest keeps connectivity while the sweep declines to judge it. Host-level unreadability *is* correctly separated (`:139-148`); only the in-loop case is conflated.

**B3. The `/manage` instance projection leaks host identity and raw daemon errors.** Clause `:2747`: "no server id, no socket/daemon addresses, no host filesystem paths, no raw runtime errors — field-level, not just the wire path." I verified `ManageInstanceResource.java:116-118` includes `new InstanceOverviewPage(this)` — the same class the admin resource uses, with **no panel-aware branch** — and `InstanceOverviewPage.java:86-89` unconditionally puts `hostName`, a `hostTarget` carrying the numeric `serverId`, and `installError` into the template vars; `instance-overview.hwk:42` renders the host link. `installError` is stamped with unfiltered daemon/transport text (`InstanceInstalls.java:203-206, :257-259`). Second surface at `InstanceProvisioningPage.java:98`. The FORM half of the projection is correct. Disclosure to an already-authorized tenant (host display name, numeric id, daemon error text — no credentials), but it is exactly the "field-level, not just the wire path" failure the clause names. The `/manage` projection test asserts capability refusals only and never asserts a rendered field, so it neither covers nor contradicts this.

**B4. The environment-variable write lane is wider than the UI — the one place the API doc's opening principle is violated.** `paas-api.md:7` promises "nothing in the API is a wider door than the admin/manage UI". I verified `PaasApi.visibleEnvironment` (`:514-534`) gates on `isAdmin` **OR** (`coversInstanceVocabulary` — a scope token, not a record capability) **AND** `Projects.mayCreateInto` — bare group-membership expansion. The service then deliberately declines to gate: `InstanceVariables.java:163-167` returns immediately when `instanceId == null`, with an AIDEV-NOTE stating "EnvironmentVariableResource is admin-only". And it is: registered only on `HohenheimPanel`, absent from `ManagePanel`'s peer list. The written value is live — `InstanceVariables.valuesFor` folds environment rows in as the baseline and `env.putAll(declared)` lets an environment row **override an instance's own `environment_variables` entry** on instances the writer holds no capability over. *Narrowing:* `{{KEY}}` substitution only reaches tokens the instance author already placed; and in the normal shape every project member already holds MANAGE on project-created instances, so this bites only where an admin placed an instance into a project's environment without adopting it. *Also note:* `paas-api.md:70` **does** state "requires project membership plus instance-manage scope", so this is an internal contradiction between the doc's principle and its own row.

**B5. Docker tier has no log limit and no ephemeral/root disk limit.** Clause `:2583`: "Runtime limits also cover pids, logs and ephemeral disk." I verified: pids ship (`ContainerHardening.java:316`); `ResourceLimits.applyTo` writes **only** `Memory` and `NanoCpus`; and `grep -rniE 'logconfig|max-file|max-size|log-driver|StorageOpt|storage_opt' src/` returns **zero hits repo-wide**. Every tenant container inherits the daemon's default json-file driver with no rotation. Root disk is Incus-only, and `DockerContainerKind.SETTINGS_SCHEMA` declares no root-disk field, so the tier is not merely unenforced — it is *undeclarable*. There is no host-level disk observer either. The code states the consequence itself (`InstanceOverviewPage.java:104-106`: "Docker enforces no root quota and stamps nothing, so the whole tier is unmeasured by contract"). Tenant-driven host-availability DoS; reachable today.

**B6. Git build runs UNCONFINED when a site has no system user, while the docblock says such a build is refused.** I read `GitDeployment.java:423-429`: `isolateBuild()` returns **true** (build proceeds) when `runAs == null`, logging a warning only — so `ProcessNetworkPolicy` is never applied and untrusted repo content executes as the daemon's own identity. *Correction to the auditor:* `confinementPrefix()` never sees `runAs` and returns null only when systemd cannot enforce a cap, so on any systemd host the cgroup half *is* applied and only the network half is missing. Counterweight: `WorkloadIdentity.forSite` throws whenever `enforcementRequired`, and `process.require_dedicated_user` defaults **true** with no "enable later" gate, and is unconditional for any tenant-managed site failing closed on an unreadable grant table. So this needs an explicit operator opt-out. The docblock's justification ("a site whose runtime cannot be isolated cannot spawn either") does not hold for the STATIC git site type, which builds but never spawns.

**B7. Posture escalation skips preflight revalidation.** `IncusPreflight.java:92, :140` freeze required-ness at probe time from the *then-current* posture; `HostPreflight.store` persists `PREFLIGHT_OK = report.passed()` where `passed()` counts only required failures. Nothing re-evaluates on a posture change: `ServerModel`'s only hooks are the three at `:328-330`, and the only caller of `runAndStore` is a manual row action. So a host preflighted while `trusted_only` records `container_userns=FAIL` / `container_seccomp=FAIL` as non-required, keeps `preflight_ok = true`, and after a flip to `shared_container` both admission gates pass. *Narrowing:* the kernel-**lane** half re-gates live (`requireKernelTruth` demands stored `KERNEL_LANE_CHECK == PASS`), so only the userns/seccomp pair survives unchecked; Docker is unaffected because those are advisory there anyway. Fix without re-probing: the per-check `required` flag is already stored — recompute the verdict against the *current* posture.

**B8. Read-only rootfs not implemented and no template flag for it.** Clause `:239-243` lists it among Docker hardening. Four of five controls are present at the single funnel (CapDrop ALL, no-new-privileges, bind mounts refused, seccomp kernel-verified). `ReadonlyRootfs` is absent everywhere, and — worth noting — it is **not in `ESCAPE_KEYS`** either, so the single-funnel doctrine would not notice a future caller setting it directly. Lowest-value of the five: the clause is conditional ("where the template allows") and this workload class writes to its rootfs. But the omission is recorded nowhere as a decision.

**B9. No bandwidth or connection limits on either runtime, including Incus which supports them natively.** Clause `:2553`. Verified: `IncusInstanceRuntime.applyLimits` (`:508-522`) maps **only** memory and cpu, and `isManagedKey` (`:421`) claims the whole `limits.` namespace as driver-owned — so an operator who hand-sets `limits.ingress` has it erased on the next converge. No manual workaround exists.

**B10. Device-mutator authorization has zero test coverage, and the row claims otherwise.** `proxmox-use-inventory.md:158-162` claims the surface test asserts "every refusal lane (capability, quota, daemon)". I read `InstanceDeviceSurfaceTest.java:261-341`: step 1 is `devices_unsupported` — a **driver** capability on a docker kind, not an authorization decision. No step drives a caller who can see the instance but lacks CONFIG. `grep -rln 'attachDisk|/devices|InstanceDevices' src/browserTest` returns three files, none of which covers it. So `requireOperationCapability(instanceId, CONFIG)` at `InstanceDevices.java:53/:89/:129/:161` — the only barrier between a VIEW-only delegate and deleting a backing volume — is untested, and `ManageInstanceDeviceResource.java:41-48` scopes the read predicate to VIEW, so a VIEW-only delegate *is* shown the device list and the edit route. Nothing is exploitable today (the check is present at all four mutators); this is regression risk plus a false evidence claim.

**B11. DNS federation's owner-side records API is admin-permission-gated with no per-zone scope, and the doc describes it as key-gated only.** `dns-federation.md:102-105`. Verified: all four `API_DNS_*` endpoints carry `.requiresPermission("hohenheim.admin.access")` (`HohenheimEndpoints.java:811, :821, :831, :842`) and the handler makes no per-zone decision — its own AIDEV-NOTE (`HohenheimHandlers.java:557-563`) says "relax it, or mint admin-permissioned keys for a narrower purpose, and every such key can edit **EVERY** primary zone." ### TIER C — correctness

**C1. No per-instance lock on destructive operations.** Clause `:3136` requires destroy to "hold a per-instance lock".
