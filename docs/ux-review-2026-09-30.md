# Admin UI review, 2026-09-30

Hands-on walkthrough of the admin as a first-time operator: a scratch install (empty database, local Docker,
own ports), current code (6564a495 on the 09-30 framework). Every finding below was seen on screen or measured
with a request; nothing is inferred from code.

Not walkable on that machine: a RUNNING workload. The laptop has no btrfs volume storage and nftables needs a
password, so the host can never be admitted; Console, Files, Stats, Shell and deploy results are unreviewed.

## Verdict

Not janky, but too CRUD-like, and in a few places misleading. The screens are consistent, most refusals say
why, and some pages are genuinely good (host overview, create-from-template, the instance "cannot start yet"
panel). But the admin is organised around the database, not around jobs: a task like "put a site online with
HTTPS" or "password-protect a folder" crosses four or five screens, has dead ends, and at the end the admin
still shows a green badge for a site every visitor gets a 503 from.

## What is broken or misleading (fix regardless of redesign)

1. A new domain defaults to Force SSL with no certificate: every visitor gets "503 HTTPS required", and nothing
   in the admin warns. The Sites list shows a GREEN "HTTPS" badge for that site (it means "forced", not
   "working"). The domain help says Force SSL "redirects to HTTPS"; without a certificate it 503s.
2. `ssl.letsencrypt_enabled = false` does not stop a manual certificate request: it registered a PRODUCTION
   ACME account and placed an order. The form never says it talks to Let's Encrypt production, does not check
   that the name resolves to this proxy first, shows the raw ACME error on failure and WIPES the form (domains,
   name) and drops the site context.
3. A protected path whose access list has no rules is silently open ("a list without rules lets every request
   through"); a new rule also starts switched off. Protecting a path can therefore look done and protect
   nothing.
4. Host admission: the list offers Admit, Admit refuses "no passing preflight", and Preflight is hidden in the
   overflow menu. Preflight reports no result; the second refusal ("last passed preflight under a different
   posture ... only counted as advisory then ...") is unreadable. The refused Admit button turns green.
5. Dead end: the protected-path Access list picker says "No results found" with no way to create one.
6. Orphans and broken links: Backup targets has a page but no navigation entry; the dashboard's backup
   attention item lands on the top of Settings, and the setting it names is a free-text target NAME with no
   picker.
7. Visual bugs: on a stored secret field "Show value" and "Clear stored value" overlap; error toasts survive
   navigation; the access rule title is the literal placeholder "Password: Username".
8. Wrong fields: choosing Static on a new site ENABLES the Instance picker; LXC and VM kinds are offered with
   no Incus host; Deploy and Restart are enabled on an instance that cannot start.

## Why it feels CRUD-like

- Navigation is one entry per model: 23 entries (Projects, Sites, Instances, Runtime images, Stacks,
  Databases, Database engines, Instance templates, Git providers, DNS zones, Certificates, Access lists,
  Released hostnames, Users, Roles, Activity, Inbox, Notification channels, Settings, Build info, Hosts, ...).
- Site and instance are separate worlds. An app online = create instance, deploy, create site with an Instance
  upstream, add domain, request certificate: three areas, no flow between them.
- Record pages open on a raw list or form, not on "what is this and is it OK": a site opens on its Domains tab,
  a new instance on "Edit instance" (full raw config, kind cards still changeable), an access list on its edit
  form. Headings read "Overview" with the record name small and grey.
- The template catalogue (Velocity, Minecraft, WordPress) is the best way in, and "New instance" never offers
  it; WordPress is six rows, one per PHP version.
- 15 tabs on an instance, three of which run commands (Console, Shell, Exec); "Migrate to host..." is an
  action shown as a tab.
- Activity and the dashboard feed log table rows, not operator actions: "Created · Lease", "Created · Quota
  hohenheim:host_mem_mb:1", "Created · * · Grant", "Bootstrap state". One template create = six rows.
- Settings is "every configurable value": 68 groups, duplicate names (Database x2, Storage x3, Cms x2),
  framework internals (Pool, Pre-route admission, Legacy API, Clock).
- Language leaks the implementation: raw setting keys in help and attention items, "the declared contract, not
  a failed reading", "ports this instance holds in the ledger", "Posture: Trusted only", "record-specific
  access", ACME HTTP-01/DNS-01 up front. "Access" means both who may MANAGE a record and who may VISIT a site.

## What is good (keep and spread)

- Host overview: state badges, a plain "No volume storage" explanation, a per-check preflight report with
  required/advisory, capacity and workloads.
- Create-from-template: a description and three fields.
- Instance overview's "This instance cannot start yet ... Fix this on host local".
- Honest copy where it exists (the Rules tab says exactly what an empty list does), choice cards with one-line
  help for upstream and kind, empty states with one action, a searchable Settings page, phone-width reflow.

## Proposals (for decision; nothing is built)

P1. One "Put something online" flow. Pick WHAT (template, git app, container image, static folder, redirect,
    address), WHERE (host chosen automatically, override possible), the HOSTNAME, HTTPS (automatic, with a DNS
    pre-check and a plain explanation when the name does not point here yet). It creates instance + site +
    domain + certificate behind the scenes and ends on the app's page showing the live URL. The dashboard's two
    competing checklists become this one flow.

P2. Every record page opens on a status Overview: one health line ("Live at https://docs.example", or "Visitors
    get 503: HTTPS is forced but there is no certificate - Request one / Stop forcing HTTPS"), then what it
    serves, its domains and certificate state, its protection, its instance. Tabs hold the detail. Headings are
    the record's name.

P3. Honest defaults and badges: Force HTTPS switches on automatically once a certificate is active, never
    before; a TLS badge shows working / expiring / missing, never "forced". A protected path must have a
    working rule to save, or says loudly that it is open.

P4. Navigation of about eight entries by job: Dashboard, Apps (sites, instances, stacks as one list with a
    type column), Databases, Hosts, Domains (DNS zones, certificates, released hostnames), Access (users,
    roles, access lists), Activity, Settings (backup targets, notification channels, templates, runtime images,
    git providers, database engines, build info as sections).

P5. Instance tabs from 15 to about 7: Overview, Console (console, shell and exec as modes), Files, Metrics,
    Backups (snapshots, backups, schedules), Configuration (edit, attached databases, provisioning), Access and
    History; Migrate, Deploy, Restart as header actions that are disabled with the reason when they cannot run.

P6. Protect a path in place: on the site, "Protect a path" asks the path and HOW (password, network, sign-in)
    and builds the rule inline; reusable access lists stay as the advanced option, creatable from every picker
    (plumage `pl-select` createLabel already exists for this).

P7. Host admission as one "Check and admit" action: runs preflight, admits on pass, otherwise lists the failed
    required checks first, each with its fix.

P8. Operator language: activity narrated per action with plumbing rows (lease, quota, grant, bootstrap) hidden;
    attention items deep-link to the exact field or page; no raw setting keys in UI copy; Settings shows
    Hohenheim's operator groups first and framework internals behind "Framework".

## Where each fix lives

Framework (zenit-cms, plumage), benefiting every app: overview-first record pages and name headings, create
from a picker, activity narration and hiding plumbing models, toasts cleared on navigation, the secret-field
overlap, fields irrelevant to the chosen variant hidden, settings grouping and deduplication, actions disabled
with a reason. Hohenheim: the flows and copy (P1, P3, P6, P7), its navigation (P4), its instance tab set (P5),
the dashboard, the defects in section 1.

## Decisions needed

1. Merge site and instance into one "App" in the UI (P1, P4)? The data model can stay as it is.
2. Force HTTPS: automatic once a certificate exists (P3), instead of on by default.
3. Scope and order: section 1 fixes first as one wave, then P2 + P3 (framework record-page shape), then P1,
   P4-P8 as a redesign pass on the Arcana model.

### /manage

- Only the admin account exists on Starfleet, so `/manage` could only be seen as the admin, who owns every record:
  every list shows the whole installation. A real tenant view (scoping, missing actions, leaks) needs a tenant
  account with a granted site and instance; creating one was out of scope for this read-only walk.
- Seen as admin: the instance overview under `/manage` offers Deploy, More, Refresh but no Restart, while
  `/admin` offers Restart. Unverified whether that is the intended tenant placement or a missing placement.
- The `/manage` instance tabs mirror `/admin`'s, so S7-S16 apply there too.
