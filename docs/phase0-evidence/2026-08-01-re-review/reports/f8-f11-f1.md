## ITEM 1 (F8) — contextual resolution now defers by default

**Behaviour change.** Route matching is STRUCTURAL for every endpoint: a
`contextResolver` parameter (`ModelParam`) never queries during matching. It resolves in
`HttpConduit.processRequest`, after the whole middleware chain. An endpoint gated only by
an `AuthRegistry` path baseline therefore costs zero database reads on an anonymous
refusal, and an existing vs missing record answer identically.

**Architectural responsibility.** Deferral was keyed on `Endpoint.requiresAuthorization()`,
which only knows the endpoint's OWN `loginRequired`/`requiredPermissions`. A path baseline
lives in zenit-auth middleware, downstream of core and after `resolveEndpoint()`, so core
cannot see it. Core now takes the safe answer as the default and makes match-time
resolution the DECLARED exception (`Endpoint.Builder.resolveContextualDuringMatch()`).
This converges with `WebSocketEndpoint.getParameterMatches`, which already defers
unconditionally; I followed its spelling (`context.deferringContextual()`) rather than
inventing a second seam. No new mechanism: `RouteMatchContext.deferringContextual()` and
`MatchResult.resolveDeferredParameters` are E4's existing seam.

**Files.** `common/routing/Endpoint.java` (field, builder flag, builder method, rewritten
AIDEV-NOTE at the decision site), `zenit/CLAUDE.md` (the ModelParam paragraph stated the
old rule and was now false).

**Tests.**
- NEW `AdmissionRateLimitHttpTest.aBaselineGatedContextualParameterResolvesOnlyAfterTheBaseline`
  — 4-step journey with a new `BASELINE_MODEL_ROUTE` endpoint (ModelParam, NO endpoint gate)
  and a new weight-20 `a06_path_baseline` middleware standing in for zenit-auth's
  `AuthRegistry` baseline read. Asserts zero reads on both anonymous refusals, identical
  status AND body, the row still reaching the handler when authorized, and 404 for an
  authorized miss.
- `ModelParamTest.plainFieldParamLoadsMatchesAndComposes` BROKE. Diagnosis: it was pinning
  the OLD default, not a regression — step 3 asserts the fall-through lane (missing row =>
  route does not match), which is exactly what the opt-in now buys. Fixed by declaring
  `.resolveContextualDuringMatch()` on the `ARTICLE` fixture, and I ADDED a step 4 with a
  second fixture (`DEFERRED_ARTICLE`, no opt-in) pinning the new default: matches
  structurally, `getParameter` is null, `hasDeferredParameters()` true, an existing and a
  missing row match identically, and only `resolveDeferredParameters` reports the miss.
  Both lanes are now covered where only one was.
- `AdmissionRateLimitHttpTest.MODEL_ROUTE` declares the opt-in, so
  `missingModelRowFallsThroughToCompetingCandidate` and
  `existingModelRowWinsTheEqualSpecificityTieBreak` keep their meaning. That is the whole
  breakage population the recon predicted.

**Consumers.** Workspace-wide grep for `contextResolver` and `ModelParam.` across javaweb
+ hohenext, excluding `build/` and zenit core itself: ZERO hits. No app behaviour changes.
`HohenheimEndpoints` `SITES_DEPLOY`/`SITES_ROLLBACK`/`SITES_PROCESS_*` can now be upgraded
to `ModelParam` safely; before this commit that upgrade would have reinstated the pre-E4
oracle.

**Limitation.** The opt-in is honest about what it costs: it declares the route's existence
public. Nothing enforces that an author who reaches for it has thought about it beyond the
javadoc; there is no compile-time or boot-time diagnostic pairing it with a gate.

Commit `cb3750a`.

## ITEM 2 (F11) — ScopedCspMiddleware consults the route guard

**Behaviour change.** `ScopedCspMiddleware.claimingRoutesOf(namespace)` now asks both
questions the router asks — does the route pattern match, AND does the endpoint accept the
match (`Endpoint.acceptsMatch`, i.e. the `matchWhen` guard). A guarded endpoint no longer
claims a path it declines and does not serve.

**Files.** `server/http/ScopedCspMiddleware.java` (the loop body inside the existing
`claimingRoutesOf`, plus the AIDEV-NOTE, which now records that the claim asks both
questions and is consequently as time-varying as routing itself — a registry-reading
guard such as zenit-cms' `panelSlugIsRegistered` answers per request, which is the same
answer the router would give at that moment). `zenit/CLAUDE.md` one clause.

**Tests.** Two steps appended to the existing 5-step journey
`ScopedCspHttpTest.derivedNamespaceClaimsMatchRoutesExactly`, with a new `MODULE_GUARDED`
fixture carrying `matchWhen(match -> "known".equals(...))` — the zenit-cms shape. Step 6
claims `e6-panel/known`, step 7 refuses `e6-panel/unknown`. Step 7 failed before.

**Consumers.** None. `claimingRoutesOf` has one production call site (`ZenitAuth.java:269`,
namespace `zenitauth`) and no zenit-auth endpoint carries a guard, so nothing changes for
`AuthCmsResourcesIntegrationTest`'s pinned assertions. Impact if it had been reached was a
wrong CSP header, not a privilege gain — kept to a one-line change accordingly.

Commit `b9acefe`.

## ITEM 3 (F1) — DECISION: implement the refusal, in `FieldRules.define`

**I did NOT implement canonicalization.** The recon's falsification holds and I verified it
independently: `Vocabulary.Builder.add` applies no test of any kind
(`Vocabulary.java:98-106`), so forging a same-named field buys zero privilege over using
the schema's own `.secret()` constant. Canonicalizing would close nothing.

**What I found instead, and it is stronger than the recon's framing.** The `isFilterable()`
gate is not merely "missing on explicit vocabularies" — it exists on every OTHER path and
is missing on the derivation they all share:

| site | pre-checks `isFilterable()` |
| --- | --- |
| `SchemaVocabulary.of` (`:43-47`) | yes, skips |
| `RecordSource.Builder.deriveVocabulary` (`:1314-1318`) | yes, skips |
| `RelationRules.define` (`:69-73`) | yes, THROWS |
| `VariableDefinition.forField` -> `FieldRules.define` | **no** |

`RelationRules` already throws `IllegalArgumentException` on a non-filterable related
field, at exactly this altitude, with exactly this policy. So the refusal is not a new
mechanism and not speculative scaffolding — it is the SAME gate, moved from three callers
into the one place a `Field` becomes a rule variable, which is the definition of killing a
parallel API. That resolves the CLAUDE.md "ships unwired" objection: it ships with three
existing consumers that already agree with it, one of which becomes redundant.

**Does it break the documented escape hatch?** No. The facet's documented purpose is
widening the variable SET beyond the projection; that is untouched — `vocabulary(...)` still
accepts any `VariableDefinition`, and every kind factory (`text`/`number`/`bool`/...) with a
hand-written `Compiler` still works. What is refused is only the lane where the FRAMEWORK's
own field-derived criteria factories build the criteria over a field the field itself
declares unfilterable. That lane is reached by accident (`forField(SECRET_TOKEN)` reads as
if the framework vetted it); the `Compiler` lane is reached deliberately.

**Honest about the half it does not close.** A hand-written `Compiler` lambda
(`VariableDefinition.java:56-59`) can emit `SECRET.startsWith(x)` and no field-level check
can inspect a lambda. The refusal closes the tidy half only. I judged that worth shipping
because hohenheim is going public, a secret column behind `STARTS_WITH` is a real character-
at-a-time disclosure primitive, and the untidy half is unambiguously the author's own
deliberate act while the tidy half was silent. This tradeoff is written into the AIDEV-NOTE
at `FieldRules.define` so the next reviewer does not re-raise it.

Side benefit, not the motive: `.encrypted()` fields are also non-filterable, and the ORM
already refuses value criteria on them at query time. Refusing at build time turns a
runtime 500 into a declaration-time error.

**Files.** `common/orm/query/rules/FieldRules.java` (the refusal + AIDEV-NOTE),
`VariableDefinition.java` (`@throws` on the public `forField`), `RelationRules.java` (a
comment recording that its pre-check now only exists to name the RELATION in the message —
policy is not duplicated, the diagnostic is), `zenit/CLAUDE.md`.

**Tests.** Steps 4 and 5 appended to `SchemaVocabularyTest.fieldGateJourney`. Step 4:
`supportsField(secret)` is still TRUE (unsupported-TYPE stays a different refusal),
`forField(secret)` throws, `forField(filterable(false))` throws, and
`Vocabulary.builder().add(forField(secret)).build()` therefore cannot smuggle one in.
Step 5: an ordinary field still derives, and a hand-written `Compiler` lambda still builds
a working variable — the documented out-of-reach case, asserted rather than only described.

**Consumers.** Zero production `RecordSource.vocabulary(...)`/`vocabularyFrom(...)` call
sites in either workspace; `RelationRules` already refused the same input. `RelationRulesTest`
(7) and `RuleCompilerTest` (6) pass unchanged.

Commit `cdffae3`.
