## B2

```
Issue: B2 - deleting/disabling/degrading the last administrator locks out the install
User-facing behavior changed: any write that would leave zero enabled administrators
  is refused with a form-level violation and rolls back entirely (the user row, the
  grants deleted earlier in the same transaction, the role's grants and memberships).
  Deleting/disabling/degrading a NON-final administrator still works unchanged. The
  toggle-enabled row action now runs in a transaction (it previously ran bare).
Architectural responsibility changed: new `AdministratorGuard.enforce(Runnable)` in
  zenit-auth server - a cross-write invariant, not a button confirmation. An
  administrator is an ENABLED user that effectively holds auth.admin.access +
  auth.users.edit + auth.grants.manage, decided ONLY through the resolver
  (group expansion, deny-wins, wildcard specificity). PermissionResolver gained
  `decideStoredUser` (cache-free): the per-request walk memo would otherwise judge
  the PRE-mutation world from inside the transaction. The guard is PRESERVING, not
  asserting: an install that already has no administrator is never blocked.
  Concurrency: candidate user rows are locked FOR UPDATE in primary-key order before
  the count (ordered acquisition, no deadlock); backends without row locking skip it.
Files changed: zenit-auth server/AdministratorGuard.java (new), PermissionResolver.java,
  GrantService.java (deleteDirectGrant now transactional + guarded),
  cms/AuthUsersResource.java (persist/update/delete/toggle-enabled),
  cms/AuthRolesResource.java (persist/update/delete), microcopy en.json.
  All EIGHT enumerated paths are covered; path 6 (role slug edit) is closed by B3's
  immutability instead of a guard.
Tests added or changed:
  - AuthGrantAdministrationTest.everyWritePathPreservesOneEnabledAdministrator (8 steps:
    non-final delete OK, final delete refused + rollback, disable refused, grant diff
    refused, membership removal allowed-then-refused, role delete refused + rollback,
    role grant diff refused, GrantService.deleteDirectGrant refused).
  - AdministratorGuardPostgresTest (new): two threads, CountDownLatch barrier, each
    deleting one of the last two administrators through the real resource path -
    asserts EXACTLY one delete wins and one administrator remains.
  - AuthCmsResourcesIntegrationTest (order 9): the delete ROUTE - other admins delete
    fine (302), the last one rerenders (200) with the row and its wildcard grant intact.
Observed pre-fix failure:
  "step 2: the last administrator must not be deletable ==> Expected
   be.elevenways.zenit.common.validation.Violations to be thrown, but nothing was thrown."
  "step 2: the refusal must rerender the form:  ==> expected: <200> but was: <302>"
Verification command and result: same runs as B1 (16 targeted passed, 142 full passed).
  The Postgres barrier passed in 3 independent JVM runs.
Backend/browser coverage: SQLite (functional + HTTP), PostgreSQL (concurrency barrier).
Known limitations or decisions:
  - The administrator oracle is the 3-permission conjunction. A host with its own
    permission vocabulary has zero administrators by this definition, so the guard is
    inert there (deliberate: it only preserves an invariant that already held).
  - GrantService.createDirectGrant is NOT guarded (a per-entry guard inside a diff would
    judge intermediate states); the diff callers are guarded as a whole.
  - The candidate set is read before the lock, so an administrator created by another
    transaction between read and lock is outside the mutual exclusion; the before/after
    counts are still recomputed fresh, so the outcome stays fail-closed.
Commit and push state: zenit-auth e8dcb0b. NOT pushed.
```
