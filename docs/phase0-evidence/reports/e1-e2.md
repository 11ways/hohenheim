## E1. Locale prefixes bypass AuthRegistry baselines and public prefixes

**Claim re-verified: REAL.** `AuthorizationMiddleware.java:30` read `conduit.getPath()` (raw, prefixed — `HttpConduit:387`) while routing resolved against `routeUri` (`HttpConduit:403`, stripped in `applyRouteLocale()` :479-502, before the middleware chain in `parseRequest()`). `AuthRegistry.matchesPrefix` (:89-93) is a literal `equals || startsWith(prefix + "/")`, so `/nl/account/x` matched neither the `/account` baseline nor any public prefix.

**User-facing failure.** With locale routing active, prefixing any URL with a configured locale disabled the whole AuthRegistry tier: login-only baselines, permission baselines and the setup gate. `/nl/admin/...` served admin pages to an anonymous or unprivileged visitor while `/admin/...` correctly refused them. Public prefixes broke in the same direction (a prefixed `/nl/login` would have been swallowed by the setup gate).

**Root cause / owner.** zenit-auth read the request path where it needed the canonical route path; zenit core owns the distinction (`HttpConduit.getRoutePath()`).

**Seam chosen and why.** `AuthorizationMiddleware.apply` now takes the concrete `HttpConduit` that `Middleware.Action.handle(String, HttpConduit)` already hands the registration lambda (`ZenitAuth.java:254-256`), and reads `conduit.getRoutePath()`. This is exactly the shape of the already-correct consumer `ScopedCspMiddleware` (which also takes `HttpConduit` and claims by route path). Rejected: a `ConduitAttributes.ROUTE_PATH` key (a second source of truth for state `HttpConduit` already holds — a parallel API); rejected: widening the `Conduit` interface with a `default` returning `getPath()` (silent degradation on every future implementor, and 25+ test stubs). `Middleware`'s `middlePath` derivation from `getPath()` (:75-80) is untouched, as instructed; zenit-auth registers at prefix `/` so it is unaffected either way.

**Other `conduit.getPath()` consumers checked (repo-wide + hohenheim).** No other authorization decision reads it. Non-decisions, deliberately left on the request path per G3: `SessionCsrfTokenStore:90` and `CsrfMiddleware:107` (logging), `HttpConduit:995` (error page), `Middleware:75/80` (asset prefix), `RouteLocales:159` (consumes the prefix itself). One smell surfaced, NOT fixed (out of scope, not authorization): `zenit-cms CmsShellFunctions.currentPanel` (`:242`) resolves the CMS panel — brand + nav chrome — from the raw path's first segment, so `/nl/admin/...` finds panel `nl` and renders unbranded chrome. Rendering only; the panel's access checks are elsewhere.

**Test.** New `zenit-auth/src/test/java/be/elevenways/zenit/auth/server/LocaleAuthorizationHttpTest.java` — one real-HTTP behaviour journey (`routing.locale_prefixes = "en:,nl:nl"`, own `ZenitHttpServer` on port 0, restored in `@AfterAll`): (1) unprefixed login-only baseline redirects, (2) `/nl/...` hits the same baseline, (3) unknown prefix `/zz/...` is NOT a locale (404 — authorization judged exactly what routing did), (4) a public prefix nested inside the baseline opts out both prefixed and unprefixed, (5) logged-in user passes the login baseline through the prefix, (6) permission baseline 403s that user prefixed and unprefixed, (7) unknown prefix stays unrouted on the gated route.

## E2. Callback-lane overflow discards WebSocket teardown

**Claim re-verified: REAL.** `ZenitHttpServer:601-607` overflow callback → `closeConnection` (:835-840) → `WebSocketTeardown.closeWith` → `release()` (:121-135) does the `released` CAS *first* and then `lane.execute(...)`; `SerialExecutor.execute` returns immediately `if (overflowed)` (:246-249), and `overflowed` was set at :252-258 *before* `onOverflow.run()` (:275). The later `channel.addCloseTask(closed -> teardown.transportClosed())` (:615) hits the consumed CAS. `handler.onClose` never ran.

**User-facing failure.** A connection dropped for callback-lane overload (1013) left the handler believing it was still connected: retained resources (hohenheim's process-log listeners, buffers, subscriptions) leaked for the process lifetime, and no transport event afterwards could recover them.

**Fix — how exactly-once-and-always is guaranteed on every path.**
- `SerialExecutor` gained an honest submission path: `private boolean submit(long, Runnable)` (the old `execute` body) returning false when the lane refused the task; `execute(...)` keeps its silent-drop semantics for message callbacks, `tryExecute(Runnable)` reports the fate. Queue accounting (`unfinishedTasks`/`unfinishedBytes`, pause/resume, the `overflowed` skip in `drain()`) is byte-for-byte unchanged — a refused task never enters the queue.
- `WebSocketTeardown.release` wraps the handler release in a **one-shot** `Runnable` (`onceOnly`, CAS-guarded), stores it as `pendingRelease`, and submits it with `tryExecute`. Accepted → it runs on the lane, **behind** every already-queued callback (normal-close ordering preserved). Refused → it runs on `RUNNER` (`JobRunner.create("zenit-ws-teardown")`, the existing non-rejectable lane already used for the close-handshake grace abort), which nothing about the failed connection can reject.
- The overflow callback now also calls `teardown.callbackLaneFailed()` after `closeConnection`, covering the second hole found while implementing: overflow **clears the queue**, so a release queued by an *earlier* close would have been thrown away by the lane that accepted it. `callbackLaneFailed` re-delivers `pendingRelease` on `RUNNER`; the one-shot guard makes concurrent lane-drain and RUNNER delivery collapse to exactly one execution.
- Third hole closed: `handler.onError` throwing inside the release task used to skip `handler.onClose` (the drain's catch is per-task). `onError` is now guarded and logged; `onClose` always runs.

Per path: **normal close** — CAS + lane (ordered); **overflow/full** — CAS + `tryExecute` false + RUNNER, and `callbackLaneFailed` for an already-queued release; **FIN / RST** — `channel.addCloseTask → transportClosed()`, CAS decides (unchanged); **unacknowledged server close** — `closeWith` releases immediately and aborts the transport after the grace (unchanged); **throwing handler** — guarded `onError`, drain catches the rest. Every path goes through the single `released` CAS, so at most one release; every path that can be the last event either performs it or re-delivers the one-shot, so at least one.
