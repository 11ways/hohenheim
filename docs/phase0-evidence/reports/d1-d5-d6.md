**Issue: D1 — Same-name noncanonical fields bypass RecordSource secret gates**

- **User-facing behavior changed:** A `RecordSource` declaration that hands a facet any `Field` instance the model schema does not own now fails at `build()` — i.e. at registration/boot, before any request is served. Previously such a source built fine and served data: the build gates inspected the *passed object's* flags while `Field.getValue(Row)` reads `row.get(name)`, so a brand-new non-secret field named `secret_token` passed the secret gate and then projected/searched/sorted the real secret column.
- **Architectural responsibility changed:** `RecordSource.Builder.build()` now canonicalizes before validating. Facets covered: `project`, `sortable` (= the bucketable whitelist behind `sortableFieldNamed`), `search` (explicit; derived search already comes from the schema), `timestamp`. Vocabulary derivation (`deriveVocabulary`) and title derivation (`displayTitle`/`firstNonBlankValue`) inherit it, since they walk those same now-canonical lists. Rule and message shape reuse the existing precedents: `Model.updateAll`'s assignment identity check (`Model.java:1240-1247`) and `Schema.setDisplayFields` (`Schema.java:333`). Resolution is `Schema.getField(name)` with `!=` identity; unknown, foreign-model and same-name impostor fields are all one refusal.

**Issue: D5 — DataItem exposes secret primary-key and timestamp facets**

- **Decision on secret primary keys: they are ILLEGAL, and enforced at model registration.** A primary key is the record's address: it rides in URLs, in form values, and in `DataItem.value` which is `@NonNull` — there is no surface that can honor `.secret()` on it and keep the record addressable. So the *declaration* is the bug, not the emission. Enforced in `Models.registerInstance` (`Models.java`), directly beside the existing `.encrypted()`-primary-key refusal, which is the only place that knows which field IS the key. `RecordSource.item()` keeps emitting the pk unconditionally and now carries an AIDEV-NOTE saying why a redaction branch there would have nothing to answer with. A corpus scan (javaweb + hohenheim, matching each model's `getPrimaryKeyField` return against that field's declaration) found no production model with a secret pk, so this refusal breaks nothing.
- **Timestamp facet:** `timestamp(field)` is now canonicalized like every other facet AND gated by `FieldRedaction.redactsWholeValue` — the stamp leaves the server inside every `DataItem`, and it was the one facet with no redaction check at all.
- **Title guard:** `firstNonBlankValue` now asks `FieldRedaction.redactsWholeValue` instead of `field.isSecret()` (the structural rule, matching the projection/search/sortable gates). Honest note: with D1 in place I could not construct a *reachable* leak through the flag half of that guard — `Schema.setDisplayFields` already refuses secret/encrypted display fields, explicit search refuses them, derived search filters on `isFilterable` (false for secret/encrypted), and the projection gate refuses them. That half is defence-in-depth. **The second half is a real, reachable leak I found and fixed:** the projection gate deliberately admits a `SchemaField` with `.secret()` sub-keys (`project()` strips them recursively), but the title fallback read the same field RAW and stringified the whole map — handing back the exact sub-key `project()` had just protected. It now stringifies `FieldRedaction.redactSubValues(field, value, row::get)`.
- **Files changed:** `RecordSource.java`, `zenit/src/common/java/be/elevenways/zenit/common/orm/model/Models.java`.
- **Tests added:** `RecordSourceTest.titleFallbackRedactsJsonSubSecrets()` (new); `RecordSourceTest.canonicalFieldJourney()` step 4 (secret timestamp refused); `SecretRedactionJourneyTest.secretPrimaryKeysAreRefusedAtRegistration()` + a non-public `SecretPkModel` fixture (kept non-public so compile-time model discovery never picks it up).

  - `a secret primary key must be refused at registration ==> Expected java.lang.IllegalArgumentException to be thrown, but nothing was thrown.` (`SecretRedactionJourneyTest.secretPrimaryKeysAreRefusedAtRegistration(SecretRedactionJourneyTest.java:936)`)

**Issue: D6 — SecretDisclosures TTL does not bound memory residency**

- **Route taken: the REAL fix, not the documentation route.** Rationale: the contract genuinely wants a residency bound, and the primitive is server-only, so a scheduler is available.
- **Why NOT the task runtime:** `ScheduledTask`/`TaskService` is cluster-claimed and datasource-backed — one instance claims a due run. `SecretDisclosures` is per-process in-memory custody (single-process BY DESIGN, per its own class doc), so a claimed task would prune exactly one instance's heap and leave every other instance's plaintext resident. Wrong mechanism; the ledger's alternative ("a narrowly owned SERVER scheduler") is what fits.
- **What was built:** a single daemon-thread `ScheduledExecutorService` inside `SecretDisclosures` (server source set), started lazily by `stash` only while a plaintext is actually parked, running `prune()` at the instance's TTL cadence, and **shutting itself down** in the sweep that empties the cache. So an idle process carries no thread, nothing needs shutdown wiring, and tests that mint instances leak none. The stash/claim sweeps are kept (cheap common case). Residency is now bounded at under 2x TTL instead of unbounded. The start/stop race is closed by re-checking `residentSize()` under the sweep lock (stash sets its entry *before* calling `ensureSweeping`, so either the sweep sees the new entry or `ensureSweeping` sees a null sweeper and restarts it) — documented inline.
- **Constraint honored:** nothing was added to common code; `java.util.concurrent` stays in `src/server`. The existing AIDEV-NOTE at the stash sweep was updated (not deleted) to record that use-driven pruning alone did NOT bound residency, and a new AIDEV-NOTE states the sweeper's narrowness and why it is not a `ScheduledTask`. Class doc now states the residency bound explicitly.
- **Files changed:** `zenit/src/server/java/be/elevenways/zenit/server/security/SecretDisclosures.java`.
- **Tests added:** `SecretDisclosuresTest.anExpiredDisclosureIsSweptWithoutAnyFurtherUse()` — stash, then NO further stash/claim, poll `residentEntries()` (the existing auditing hook) to zero within a bounded wait; step 2 stashes again after the sweeper stood down and proves the second secret is bounded too (sweeper restart).
- **Observed pre-fix failure (exact):**
  `[1. the TTL must bound residency without another stash or claim] expected: 0 but was: 1` (`org.opentest4j.AssertionFailedError`, `SecretDisclosuresTest.anExpiredDisclosureIsSweptWithoutAnyFurtherUse(SecretDisclosuresTest.java:135)`, 5166ms — it sat resident for the whole 5s deadline).
- **Verification:** post-fix `SecretDisclosuresTest: 6 passed` in the targeted run; also green in the full zenit unit suite. Platform-independent (no backend involved).
- **Known limitation:** a process killed while entries are parked exits with a live daemon sweeper — harmless (daemon threads do not block JVM exit), and no `stop()` wiring was added because the sweeper's own lifetime is already tied to whether anything is parked.
- **Commit:** zenit `4353a29` 🔒 Make the secret-disclosure TTL bound residency, not just claims. NOT pushed.
