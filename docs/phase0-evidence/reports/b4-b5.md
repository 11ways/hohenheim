## Issue: B5 — Record grants can be planted for nonexistent records

**User-facing behavior changed:** `RecordGrants.grant(...)` now refuses with `IllegalArgumentException` ("Unknown record-grant target: <model> record '<id>' does not exist (or is not live)…") when the target row is not live. A tuple can no longer be planted on a future id and activate when that id is created. Revoke/cleanup paths are untouched (you must still be able to revoke grants on dead records).

**Architectural responsibility changed:** The grantable declaration became a real object. `RecordGrants.GRANTABLE` is now `Map<Identifier, GrantableModel>`; `GrantableModel` carries, per model, how to decide PHYSICAL LIVENESS of a target row, and owns the resolution (`Models.get` → `getPrimaryKeyField` → `SubmittedValueCoercion.coerceFieldOrThrow` → `find().where(pk.eq(coerced)).first()`) — the `RecordGrantCapabilityChecker.ownerOf` precedent, never a RecordSource query, so the Wave-G10 source-existence oracle is not reintroduced and access-hidden records stay grantable.

**Declaration shape left for C6 to extend (explicit):**

```java
model()  isLive(@Nullable Row)  findLiveRow(Object)
RecordGrants.declareGrantable(GrantableModel)  // declaring form
RecordGrants.grantableModel(Identifier)        // registry read, for the sweep
```

The M007 upgrade migration must use the same definition. Nothing needs redesigning; C6 wires the soft-delete cases and the subject-orphan sweep. Note `SoftDeleteBehaviour`-attached models already fail the default liveness because the behaviour filters trashed rows out of every `find()`.

### Known limitations / decisions
1. **`declareGrantable` stays last-wins** (documented in a new AIDEV-NOTE). A liveness predicate is a lambda, so two declarations of the same intent are not value-comparable and the B4 idempotent-or-loud policy cannot be applied without breaking every consumer whose boot wiring legitimately runs twice (hohenheim's does). B4's ledger scope is the RULES registry; this is flagged for the operator, not silently widened.
2. **Race window in `HohenheimHandlers.SITES_ACCESS_ADD`**: if a site is deleted between `existingSite(...)` and `grant(...)`, the handler now throws `IllegalArgumentException` (500) instead of writing a dormant grant. Refusing is the correct outcome; converting it to a redirect is a hohenheim UX decision, not a framework one.
3. **"Access-hidden records" is guaranteed by construction**, not by an assertion: `GrantableModel.findLiveRow` uses raw `Model.find()` and never touches `RecordSource`/`AccessContext`. The tests pin it indirectly (fixture rows owned by a stranger, granting actor holds no permission). Registering a deny-all `RecordSource` in zenit-auth tests would have added a dependency zenit-auth's test set does not otherwise have; the guarantee is stated in the class AIDEV-NOTE instead.
4. **`grant` now costs one extra SELECT per call** (the target lookup). The query-budget test (`capabilityCheckBatchesToOneQueryPerSubjectType`, 5 selects) is unaffected: it measures the CHECK path, not the write path.
