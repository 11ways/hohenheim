## F5 — Confirmation replay loses submitter semantics and can leave a sticky replay marker

**Claim re-verified at HEAD:** both halves REAL. `CmsConfirmFunctions:133` published `new ConfirmRequest(confirmation, form, null)`; `perform` set the marker then called `requestSubmit` unconditionally. Also verified the mechanism assumptions: `DirectiveTranspiler:125-128` resolves ACTIVATION to `submit` on a `<form>`, `BrowserDominoEvent:76-78` wraps a `submit` event as `BrowserDominoSubmitEvent`, and hawkeye's own soft-nav path is fully submitter-aware (`createNavigationRequest:1172-1201` honours `formaction`/`formmethod`/`formenctype` and `createFormQueryString(form, submitEvent)` includes the submitter entry) — so the confirmation lane was the only place that dropped it.

**User-facing behavior changed:** a confirmed submit on a form-lane carrier now posts to the activating submitter's `formaction` carrying its `name=value` entry (and honouring `formnovalidate`), instead of falling back to the form's own `action` with no submitter field — i.e. a confirmed "Delete" no longer performs whatever the form's default action is. Second: after a replay the browser declines (constraint validation), the operator's next genuine submit is confirmed again instead of executing the destructive action with no dialog.

**Architectural responsibility changed:** none. No new channel (G1 preserved): the fix fills the existing `ConfirmRequest.submitter` slot and bounds the existing `REPLAY_MARKER`'s lifetime to the `requestSubmit` call.

**Marker lifecycle guarantee:** `perform` sets the marker, calls `request.submit()`, and in a `finally` removes the marker **if it is still present**. The re-entering handler (`hold`, form lane) consumes it synchronously during `requestSubmit`'s submit-event dispatch, so "still present after the call returns" means exactly "no submit event fired" — the declined case. There is no path where a marker outlives the call that produced it, and therefore none where a later, unconfirmed submit can consume one.

**Files changed:** `zenit-cms/src/common/java/be/elevenways/zenit/cms/common/render/action/CmsConfirmFunctions.java` (new private `submitterOf(DominoEvent)`, form-lane publish, `perform` try/finally, one new AIDEV-NOTE; the existing AIDEV-NOTE kept and its now-wrong last clause corrected).

**Tests added:** `zenit-cms/src/browserTest/java/be/elevenways/zenit/cms/test/browser/ConfirmReplayBrowserTest.java` + fixture `zenit-cms/src/browserTestCommon/templates/test/confirm-replay-fixture.hwk` (a form carrier, two submitters with distinct `formaction` + `name/value`, a required control, three POST sink endpoints).

So it is neither a deliberate test of the syntax nor a working re-trigger — it is dead filler that happens to spell the forbidden idiom. Replaced with an honest re-assertion of the same fact the fixture exists to prove (`mountref = popupEl != null ? "live" : "null"`), which makes `mountref` report the portalled `:ref`'s liveness **after** the open transition and not only at mount, plus a comment recording why the old line could never have worked. Behaviourally identical in the passing case (equal value, skipped write); it now flips to `"null"` if the ref ever dies on open. `comboKeydownSeesSharedPopupRef` does drive `open = true`, so the watch really runs.

**Evidence used instead of a counterfactual** (this is a judgement/no-behaviour-change item): the `setStoredValue` early-return, the field's declared `String` type, the three cited test assertions, and `git blame`.
