## Issue: D2 — FormSecrets misses structural and localized secret shapes

**User-facing behavior changed**
- A `.secret()` **parent** `SchemaField` now masks its *whole* scope (every leaf), and a keep-blank submit restores every leaf instead of persisting blanks.
- A **`ListField` whose ITEM field is secret** now masks/marks/keeps/clears exactly like a secret list (previously echoed in full).
- A **localized** secret now masks *per locale* keeping the locale map, and a keep-blank submit restores each stored translation. Previously the whole locale map was flattened to `""` on render and a keep-blank submit **wiped every stored translation** (data loss).
- A dynamic (`schemaFrom`) scope whose discriminator resolves to **no** schema is now dropped instead of passed through raw (unclassifiable keys are over-redacted, FieldRedaction's stance).
- `{name}__clear` now works for a localized secret (empties every submitted locale) — previously impossible.

**Architectural responsibility changed**
One walk, entry-kind first then field-shape, over an **exhaustive pattern switch on the sealed `FormEntry` set** — a new entry kind is now a compile error rather than a silent fall-through into the scalar branch. Secrecy is a named structural rule in its mechanism home: new `FieldRedaction.hidesWholeValue` (the editor tier: `isSecret()` + the list-item rule), beside the existing `redactsWholeValue` (derived-surface tier, includes `isEncrypted()`). A `Mask.MARK`/`Mask.BLANK` mode says whether the consuming renderer has a stored-secret channel.

**Entry kinds enumerated, and the decision for each**
| Kind | Decision |
| --- | --- |
| `Plain`, `Select`, `Array`, field-linked `Embedded` | leaf rules (list / string-map / scalar), unchanged semantics |
| `Nested` | recurse; secret parent ⇒ every leaf secret; unresolvable sub-spec ⇒ scope dropped |
| `Records` | walk each row against `subSpec()`, paired by `__id`; **BLANK** mode |
| `Localized` | per-locale, structure never flattened; **BLANK** mode; entry-level clear |
| `Computed` | untouched — recomputed from siblings, dropped by coercion |
| `RelationPick`, `RelationMultiPick` | untouched — a picked id is a reference, not a payload; masking would break the picker |
| `Upload` | untouched — transport is a file part, stored bytes never echoed |
| `QueryRules` | untouched — secret fields never enter a rule vocabulary |
| field-LESS `Embedded` | untouched — owns its own transport |

**FALSIFIED ledger/recon claim (gap 6)** — "`isSecret(FormEntry)` ignores `isEncrypted()`, diverging from `FieldRedaction`" is **not a defect**. `zenit/CLAUDE.md` states the contract explicitly: "`.encrypted()` alone does NOT hide values from admin editors — combine with `.secret()`". Counterexample in production: `hohenheim StackFileModel.CONTENT` is `.encrypted()` **without** `.secret()` and is a normally edited config-file body; adopting `redactsWholeValue` would have masked it in its editor. I therefore added the editor-tier predicate (`hidesWholeValue` = secret + list-item rule) rather than widening the existing one. `StackDeploymentModel.SPEC` is the same shape; `StackModel.REGISTRY_PASSWORD` is both and is unaffected.

**Known limitations / decisions**
- `STORED_MARKER` is emitted only where a renderer channel exists. Records rows (`RecordFieldState`) and locale slots (`LocalizedState`) have none, so a stored value there blanks — no "a value is stored" note and no per-row/per-locale clear checkbox. Adding one needs new render state in zenit-forms; deliberately out of this fix.
- Mask inside records rows / locale maps hides **only what the server already holds** (the key/value row-shape precedent) so a just-typed secret survives a rerender instead of silently persisting empty.
- Behavior change: an unresolvable dynamic scope's typed values no longer survive a rerender (they were unrenderable anyway).

## Issue: D8 — Table-stored Records secret behavior explicitly incomplete

**Is there a real consumer? No — stated plainly.** I enumerated every table-stored list `SchemaField` in the workspace and hohenheim (spamservice `SampleModel.properties/breakdown`, QQ `content_parts`/`aspects`/`parameters`/`attachments`/`participants`, zenit-microcopy `TranslationModel.filters`, hohenheim `StackServiceModel.mounts/ports/depends_on`). **None declares a `.secret()` sub-field** (`grep -c 'secret()'` = 0 in each). The recon's candidates do not hold: hohenheim `DnsRecordResource`/`SpamserviceClientKeysResource` and zenit-ai `McpServerConfigModel` carry their secrets as scalars or `StringMapField`s inside a dynamic `Nested`, not as Records rows. I did **not** invent one; per instruction I wired the mechanism plus a **test-level consumer** — a real model (table-stored list whose sub-schema has a `.secret()` token), a real `RowResource`, real migrations and child table, driven through the real `ResourcePageEndpoints` submit/render path and a real browser.

Adjacent smell surfaced, not acted on: hohenheim `StackServiceModel.ENVIRONMENT` (a stack service's environment variables) is **not** `.secret()`, while the equivalent site-type environment maps are. That is the one place a Records-row secret would plausibly appear next; changing it is a hohenheim product decision, out of this issue's scope.

**User-facing behavior changed** — repeatable rows now participate in the secret contract: a stored row's secret column renders blank instead of echoing, a keep-blank submit restores it by `__id` (the same identity the diff-based child-table save updates in place), a typed value replaces, and a NEW row keeps what the operator typed so a resubmit never stores an empty secret. Both transport shapes are handled (canonical record list and the raw indexed scopes a validation-failure rerender carries).

**Architectural responsibility changed** — no second mechanism: `Records` is one `case` of the D2 walk, using `Records.subSpec()` as the sub-spec seam and `Records.ID_KEY` as row identity, in `Mask.BLANK` mode.

**Files changed** — same `FormSecrets.java` (Records case + `indexRecordRows`/`recordValues`/`applyToRecord` helpers). No zenit-cms/zenit-forms production code needed changing.
