Issue: C13 - SQLite thread-local transactions share one JDBC connection

User-facing behavior changed:
Pre-fix, any two threads touching one SqliteDatasource corrupted each other: a plain
write on thread B landed INSIDE thread A's open transaction, B entering withTransaction
committed A's buffered work, and B's cleanup reset autoCommit under A so A's own commit
exploded. Post-fix, transactions are thread-isolated: uncommitted work is invisible to
other threads, a concurrent plain write queues on SQLite's single writer and survives
the other thread's rollback, and overlapping transactions queue and commit independently.
Rollback removes exactly the owner's work, nothing else's.

Architectural responsibility changed:
SqliteDatasource abandoned its bespoke shared-connection design and now mirrors
PooledSqlDatasource's ownership model (the canonical mechanism): a transaction owns a
DEDICATED connection via the ThreadLocal; every other operation borrows a pooled
connection per call (internal free-list, cap 8 idle, no Hikari - test suites create
hundreds of short-lived instances and must not each spawn a pool housekeeper thread).
Chosen model = option (b), independent connections, decided by measurement with
sqlite-jdbc 3.45.1 (probes in scratchpad/probe/):
- shared-cache :memory: fails cross-connection access in ~1ms with
  SQLITE_LOCKED_SHAREDCACHE for BOTH reads and writes; busy_timeout does not apply ->
  shared-cache rejected; a :memory: URL is transparently mapped to a private temp FILE
  (deleteOnExit + close(); synchronous=OFF since :memory: never promised durability).
- file+WAL+busy_timeout: readers snapshot-read in 0ms during an open write txn; a
  blocked writer succeeded 534ms in when the holder committed at +500ms.
- BEGIN DEFERRED read-then-write upgrade fails non-retryably (SQLITE_BUSY_SNAPSHOT,
  1ms) after a rival commit -> connections run transaction_mode=IMMEDIATE; two
  overlapping IMMEDIATE transactions queued and both committed (final count 2).
Every connection gets journal_mode=WAL, busy_timeout=5000, transaction_mode=IMMEDIATE
via URL params (caller-supplied params win; verified pragmas land per connection).

Concurrency characteristics accepted (in AIDEV-NOTE on the class): WAL readers never
block, including during another thread's write transaction; writers and ALL
transactions (read-only included) serialize on SQLite's single writer, queue up to
busy_timeout, then surface SQLITE_BUSY loudly. Hohenheim HTTP reads are no longer
serialized behind transactions (they were de-facto single-connection before). Existing
file databases are switched to WAL on first connect (persistent, deliberate).
