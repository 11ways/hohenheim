## D3 — Restoring a normal revision could un-soft-delete a record

**Claim: CONFIRMED** (re-verified at zenit 24d40d4). `snapshot()` iterated all schema fields, so a snapshot taken from a *loaded live* row carried `deleted_at = null`; the apply-loop wrote every snapshot entry back.

**User-facing failure:** an admin restoring an old revision of a trashed record silently brought it back to life (in hohenheim: a deleted site, its routes and certificates).

**Root cause / owner:** the replay path had no concept of columns that belong to a lifecycle operation rather than to content. Owner: `zenit` core ORM behaviours.

**Fix (mechanism, not hardcoded strings):**
- `ModelBehaviour.lifecycleFieldNames()` — each behaviour declares what it owns.
- `Schema.getLifecycleFieldNames()` = union over attached behaviours **plus** `Schema.addLifecycleField(Field)` for models that maintain such a column by hand.
- `RevisionableBehaviour` screens that list in **both** `snapshot()` (plain + localized) and the restore apply-loop (plain + localized).

**Classified as behaviour-owned:** `deleted_at` (SoftDeleteBehaviour), `version` (OptimisticLockingBehaviour), `publish_status`/`published_at`/`scheduled_at` + `locale_publish_status` in per-locale mode (PublishableBehaviour). Derivation is by behaviour declaration; the only literals are the existing `OrmConstants` column constants inside each behaviour that already owns them. `version` keeps its "adopt the CURRENT value" special case (needed as the optimistic guard), now read inside the restore transaction.

**Downstream (named risk, closed):** hohenheim `SiteModel` has **no** `SoftDeleteBehaviour` — it stamps `deleted_at` by hand — so the framework fix alone would *not* have protected the only production consumer. Wired with `SCHEMA.addLifecycleField(DELETED_AT)` + AIDEV-NOTE (hohenheim commit `1a56057`).

## D4 — Restore was not atomically bound to `recordId`

**Claim: CONFIRMED**, with the wrong-row write reproduced.

**User-facing failure:** restoring revision N of record A could overwrite record B (snapshot PK mismatch), or insert/resurrect a record (snapshot with no PK, or a hard delete between check and save).

**Fix:**
- `recordId` is authoritative: the existence lookup queries on it, not on the snapshot's key.
- A snapshot whose PK differs from the requested key is refused as corrupt history (`IllegalStateException` naming the foreign key). A snapshot with **no** PK simply rides the requested id and still gets the existence check.
- Existence check + graft + write run in **one** `withTransaction`, with `forUpdate()` where the backend has row locks.
- The row's PK is set from the loaded current row, and the write goes through the new `Model.updateExisting(Row)` — `save` with the INSERT fallback refused. A `RecordNotFoundException` is re-thrown as the same "no longer exists" refusal.
- `withoutFindHooks()` preserved (its AIDEV-NOTE moved into the extracted `loadCurrentRow`, updated, not deleted). The "no current row" AIDEV-NOTE in the graft path was updated to record that the case is now unreachable.

**Design correction caught by tests:** my first `updateExisting` bypassed the overridable `Model.save(Row)`. `zenit-cms ResourcePageEndpointsTest.restoreRefusedByTheModelWritePipelineReportsTheSpecificViolation` failed (`expected: <enable_route_conflict> but was: <restored>`), which also means hohenheim's `SiteModel.save` route-invariant transaction would have been skipped. Reworked: `updateExisting` arms an **identity-scoped** `ThreadLocal<Row>` and calls the public `save(row)`, so subclass overrides still run and a nested save of *another* row keeps its fallback.

**Exact pre-fix failure texts** (both backends):
```
org.opentest4j.AssertionFailedError: step 2: the record the snapshot NAMES must never be written by a restore of another record ==> expected: <eight-oh-two> but was: <hijacked>
```
```
org.opentest4j.AssertionFailedError: step 2: a record that disappears mid-restore must be refused, not re-inserted ==> Expected java.lang.IllegalStateException to be thrown, but nothing was thrown.
```
The second counterfactual required a temporary revert: sources copied to a patch, `git checkout --`, run with `--skip-deps` (no publish), patch re-applied immediately.

**Six enumerated proof cases — all covered:**
| Case | Where |
| --- | --- |
| missing snapshot PK | `restoreIsBoundToTheRequestedRecord` step 3 (restores onto the requested id, row count unchanged) |
| mismatched snapshot PK | same, step 2 (foreign record untouched, refusal names 802) |
| concurrent hard delete | `restoreRefusesARecordThatDisappearsMidWrite` (before-write probe deletes the row inside the write pipeline) |
| soft delete | `restoreNeverRewindsLifecycleState` + `SecretRedactionJourneyTest` step 3b + hohenheim `SiteHistoryTest` |
| optimistic version change | `restoreIsBoundToTheRequestedRecord` step 4 (version 2 -> 3 adopted in-transaction) |
| localized secrets | `SecretRedactionJourneyTest` (6 journeys) + `PerLocalePublishableTest`, both green; the localized apply-loop and localized snapshot loop are on the changed path |

**Backends proven:** `zenit-dev test --datasources all --class RevisionableBehaviourTest` — 56 passed = 7 tests x **all 8** (SQLite, PostgreSQL, MySQL, DuckDB, CockroachDB, Firebird, MongoDB, Couchbase).

**Transactional guarantee, honestly stated:** the *refusal* (no INSERT fallback) holds on all 8 backends, because it is enforced in the save pipeline, not by locking. The *serialization* against a rival writer is real only where the backend provides it: PostgreSQL/CockroachDB and MySQL via `SELECT ... FOR UPDATE`, SQLite via the C13 engine's IMMEDIATE write lock held from BEGIN. DuckDB, Firebird, MongoDB and Couchbase report `supportsRowLocking() == false`, so there the window between read and write is narrowed to one transaction but not locked out; the worst case degrades to a loud refusal, never a resurrection. Restore transactions stay short (one indexed read, one guarded update, one revision insert), well inside SQLite's 5s busy timeout.

**Caller window NOT closed:** zenit-cms `ResourcePageEndpoints:1197` calls `RevisionRestoreAccess.blockedChanges(...)` at :1184 *before* `restore(...)`, outside my transaction. A concurrent edit between that access check and the restore is still possible; closing it needs the access decision moved inside the restore transaction, which is a zenit-cms change and out of D3/D4 scope.

## Limitations / follow-ups

1. New snapshots no longer contain `version`, `deleted_at` or publish-state columns, so revision **diffs** stop showing them (old snapshots still render theirs). Publish/unpublish and delete remain fully visible in the activity log. Behavioural change for any diff consumer that expected them.
2. `Model.updateExisting` uses a static `ThreadLocal<Row>` guard. It is identity-scoped and cleared in a `finally`, but it is a hidden channel — an alternative would be a first-class save-context flag, which requires touching `SaveToDatasource` construction on the fallback path.
3. Non-row-locking backends (DuckDB, Firebird, MongoDB, Couchbase) get no pessimistic serialization, per above.
4. The zenit-cms `blockedChanges` check-then-act window remains open (item above) — needs an owner decision on moving field-level access into the restore transaction.
5. Other apps with hand-maintained lifecycle columns must call `Schema.addLifecycleField` themselves; only hohenheim's `SiteModel` was found in this workspace.
