Issue: C7 - insertIfAbsent conflates primary-key and secondary unique conflicts
User-facing behavior changed: `Model.insertIfAbsent` returns false ONLY for the primary-key conflict its contract describes. Any other unique constraint now surfaces as `DuplicateKeyException`. Previously a secondary unique collision on a FRESH primary key answered false, telling the caller "someone else took your key" when nothing was written and the key was still free.
Architectural responsibility changed: The conflict target became explicit at each layer instead of being inferred from "a conflict happened":
  - `SqlDatasource.buildInsertIfAbsentSql` takes the primary-key column and emits `ON CONFLICT (<pk>) DO NOTHING` (was a bare `ON CONFLICT DO NOTHING` that swallowed every index). Signature threaded through the two overriders (MySQL, Firebird), both of which still return null.
  - The try/catch fallback (MySQL, Firebird) returns false only when `DuplicateKeyException.isPrimaryKeyConflict(pk)` says so, else rethrows. `DuplicateKeyException` now also carries MySQL's reported INDEX name as `constraintName` (previously Postgres-only); the C12 column-attribution logic from 1d18d89 is refactored onto a shared `mysqlKeyName` helper and otherwise unchanged.
  - Mongo returns false only for a code-11000 error naming the automatic `_id_` index; any other 11000 is wrapped in `DuplicateKeyException`.
  - Couchbase VERIFIED NOT AFFECTED and documented rather than changed: the KV document id IS the primary key, and its migration visitor degrades a declared unique index to a plain one (`orm.migration.couchbase_unique_index_unenforced`), so no secondary constraint exists to mistake for a lost race.
